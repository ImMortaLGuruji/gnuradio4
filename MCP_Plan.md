# GNU Radio 4 Model Context Protocol (MCP) Server Architecture & Implementation Plan

This document outlines the phased design and implementation plan for a **Model Context Protocol (MCP)** server tailored for **GNU Radio 4 (GR4)**. It is specifically architected for AI-driven signal processing development within environments like **Antigravity IDE**, **VS Code**, **Cursor**, and **Claude Desktop**, while maintaining strict zero-conflict isolation from the actively evolving upstream GR4 codebase.

---

## 1. Executive Summary & Design Principles

### 1.1 Objective

Empower AI coding assistants to:

1. **Introspect the GR4 Environment**: Inspect installed blocks, ports, properties, C++23 template requirements, and runtime capabilities.
2. **Scaffold & Synthesize C++23 DSP Blocks**: Generate modern, idiomatic C++23 GR4 blocks complying with the [`gr::BlockLike`](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/tests/oot-smoke/main.cpp#L12) concept, including tests and CMake orchestration.
3. **Control & Simulate Flowgraphs**: Communicate with the GR4 control plane ([`gr4cp_server`](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/tests/control-plane-smoke.sh#L11)) via REST and WebSockets to deploy, validate, and monitor signal processing pipelines.
4. **Automate Build & TDD Cycles**: Build Out-Of-Tree (OOT) modules, run CTest suites, and capture compiler/runtime errors to self-heal code.

### 1.2 The Conflict-Minimization Strategy (Zero Upstream Friction)

Because GNU Radio 4 is in active development with frequent rebases, branch switches, and refactorings across branches (`main`, `maint-4.0`), modifying core tracked files ([`CMakeLists.txt`](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/CMakeLists.txt), [`modules.cmake`](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/modules.cmake), [`CMakePresets.json`](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/CMakePresets.json)) creates severe merge hazards.

To guarantee **zero merge conflicts**, the MCP implementation uses a four-pillar isolation pattern:

```text
+--------------------------------------------------------------------------+
|                           AI Assistant (IDE)                             |
|              (VS Code / Antigravity IDE / Cursor / Claude)               |
+--------------------------------------------------------------------------+
                                     |
                          stdio / SSE (JSON-RPC)
                                     v
+--------------------------------------------------------------------------+
|                      GNU Radio 4 MCP Server (gr4-mcp)                    |
|                [Independent Directory or Out-of-Tree Repo]               |
|                                                                          |
|  +--------------------+  +---------------------+  +-------------------+  |
|  |     MCP Tools      |  |    MCP Resources    |  |    MCP Prompts    |  |
|  | (Scaffold, Build,  |  |  (Block Catalog,    |  | (DSP Code Gen,    |  |
|  |  Validate, Sim)    |  |   Schemas, Docs)    |  |  Pipeline Debug)  |  |
|  +--------------------+  +---------------------+  +-------------------+  |
+--------------------------------------------------------------------------+
          |                                                 |
          | HTTP / WebSockets (Port-Agile)                  | CLI / Environment
          v                                                 v
+-----------------------------------+     +--------------------------------+
|     gr4cp_server (Control Plane)  |     |  Installed SDK & Tools         |
|  - GET /healthz                   |     |  - source build/.../activate.sh|
|  - GET /blocks (dynamic catalog)  |     |  - CMake / Ninja SDK compile   |
|  - POST /flowgraph (deploy/step)  |     |  - CTest smoke integration     |
+-----------------------------------+     +--------------------------------+
```

1. **Decoupled Out-of-Tree Layout**:
   - Developed either in an isolated directory (`tools/gr4-mcp` or `oot/gr4-mcp`) or a standalone repository (`gnuradio/gnuradio4-mcp`).
   - Integrated with the superbuild solely via the existing git-ignored [projects.local.cmake](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/projects.local.cmake.example) hook or executed completely standalone against an active installation prefix (`GR4_PREFIX`).
2. **Interface Against Public Abstractions**:
   - Avoid private headers or volatile source-tree internal structures.
   - Interface strictly against:
     - The installed SDK public headers (`<gnuradio-4.0/...>`) and exported CMake packages (`gnuradio4::*`).
     - The HTTP/WebSocket endpoints provided by [`gnuradio4-control-plane`](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/modules.cmake#L48).
     - The runtime environment generated by [activate.sh](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/cmake/activate.sh.in).
3. **No Upstream File Mutations**:
   - Preserves all upstream tracked files untouched.
   - Custom build presets remain in `CMakeUserPresets.json` (which is already `.gitignore`d).
4. **Dynamic Runtime Probing & Fallback**:
   - The MCP server auto-discovers active GNU Radio installations via environment variables (`GR4_PREFIX`, `CMAKE_PREFIX_PATH`) or scans standard build directories (`build/dev`, `build/full`).
   - Graceful offline fallback: if `gr4cp_server` is not running, the MCP server falls back to static header parsing and template rendering.

## 2. Technical Stack Selection

- **Implementation Language**: **Python 3.11+** with `FastMCP` (official `mcp` Python SDK).
  - _Rationale_: Python is native to the SDR/DSP community, seamlessly interfaces with scientific tooling (NumPy, SciPy), supports fast subprocess execution (`cmake`, `ninja`, `ctest`), and provides asynchronous HTTP/WebSocket clients (`httpx`, `websockets`) for the control-plane daemon.
- **Protocol Transports**:
  - `stdio`: Default transport for local IDE integration (VS Code MCP extensions, Claude Desktop, Antigravity IDE).
  - `Streamable HTTP / SSE`: Optional transport for containerized development (e.g. interfacing with [containers/studio-web](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/containers/studio-web)).
- **Integration Points**:
  - [tests/oot-smoke](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/tests/oot-smoke): Serves as the gold standard for how out-of-tree blocks must compile, link, and test against the installed SDK.
  - [tests/control-plane-smoke.sh](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/tests/control-plane-smoke.sh): Serves as the blueprint for launching, interrogating, and stopping `gr4cp_server`.

## 3. Phase-Wise Implementation Roadmap

### Phase 1: Foundation & Non-Invasive Environment Discovery

**Goal**: Establish the standalone MCP daemon, safe packaging, and robust workspace auto-detection.

1. **Repository & Directory Structure**:
   ```text
   tools/gr4-mcp/                     # or standalone repo: gnuradio4-mcp
   ├── pyproject.toml                 # uv / hatchling configuration
   ├── README.md                      # Setup and IDE configuration guide
   ├── src/
   │   └── gr4_mcp/
   │       ├── __init__.py
   │       ├── server.py              # FastMCP application entry point
   │       ├── env.py                 # GR4_PREFIX, activate.sh, CMake probing
   │       ├── client.py              # Control-plane HTTP / WebSocket client
   │       ├── tools/                 # Tool implementations
   │       ├── resources/             # Resource URI handlers
   │       ├── prompts/               # Prompt templates
   │       └── templates/             # Jinja2 C++23 & CMake templates
   └── tests/
       └── test_server.py
   ```
2. **Environment Discovery Engine (`env.py`)**:
   - Detect `GR4_PREFIX` or probe `${workspaceFolder}/install` / `${workspaceFolder}/install/full`.
   - Parse active paths: binary dir (`bin/`), include dirs (`include/`), library dir (`lib/` or `lib64/`), and plugin dirs (`lib/gnuradio-4/plugins`).
   - Extract environment variables without modifying the host shell by parsing [cmake/activate.sh.in](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/cmake/activate.sh.in).
3. **Control-Plane Connection Manager (`client.py`)**:
   - Probe loopback port for running `gr4cp_server` or launch an ephemeral instance in background using `GR4CP_PORT=0 GR4CP_PORT_FILE=...` following [tests/control-plane-smoke.sh](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/tests/control-plane-smoke.sh#L47).
   - Validate connectivity against `/healthz`.

### Phase 2: MCP Resources & Introspection Tools

**Goal**: Allow LLMs to inspect the full library of GR4 blocks, ports, properties, and C++23 types.

1. **MCP Resources**:
   - `gr4://blocks`: Live JSON list of all available blocks discovered via dynamic plugin loader or static registry.
   - `gr4://blocks/{block_id}`: Comprehensive schema for a specific block (inputs, outputs, data types like `std::complex<float>`, settings, default values).
   - `gr4://sdk/block-concept`: The C++23 [`gr::BlockLike`](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/tests/oot-smoke/main.cpp#L12) concept definition, port traits, and lifecycle constraints.
   - `gr4://templates/oot-project`: Template structure for a standard out-of-tree module.

2. **Introspection Tools**:
   - `gr4_list_blocks(category?: string, filter?: string)`: Query available blocks by category (e.g. math, filter, sdr, modulation).
   - `gr4_get_block_details(block_id: string)`: Return port signatures, parameters, and documentation for any block.
   - `gr4_get_sdk_info()`: Return active GR4 version, compiler standards (C++23), enabled features (ZeroMQ, SDR, Audio), and search paths.

---

### Phase 3: C++23 Block Scaffolding & Code Synthesis

**Goal**: Enable the AI to generate production-quality, type-safe C++23 GR4 blocks that compile on the first try.

1. **Jinja2 C++23 Templates**:
   - Modern template-based header architecture conforming to GR4 design:
     - `gr::BlockLike` adherence.
     - Port declarations (`gr::PortIn<T>`, `gr::PortOut<T>`).
     - Configuration parameters and default values.
     - `processBulk(...)` / `processOne(...)` work functions.
   - Standard GoogleTest / CTest unit tests validating numerical correctness.
   - Clean `CMakeLists.txt` using `find_package(gnuradio4 CONFIG REQUIRED)` matching [tests/oot-smoke/CMakeLists.txt](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/tests/oot-smoke/CMakeLists.txt).

2. **Scaffolding Tools**:
   - `gr4_scaffold_block(name, category, inputs, outputs, parameters, is_sync)`:
     Generates `<Name>.hpp`, `<Name>.cpp`, and associated `<Name>_test.cpp`.
   - `gr4_scaffold_oot_module(module_name, destination_path)`:
     Sets up an out-of-tree CMake project structure ready for compilation and registration.

3. **MCP Prompts**:
   - `scaffold-dsp-block`: Guides the LLM to ask clarifying questions about sampling rate, data types, SIMD vectorizeability, and statefulness before writing code.
   - `port-gr3-to-gr4`: Translates legacy GNU Radio 3.x blocks (Python or C++ `gr::sync_block`) into modern GR4 C++23 zero-copy constructs.

---

### Phase 4: Automated Build, Test & Diagnostics (TDD Loop)

**Goal**: Allow the AI assistant to autonomously build, test, and diagnose errors in OOT modules.

1. **Compilation Tools**:
   - `gr4_build_oot(project_path: string, build_type: "Debug"|"Release"|"RelWithAssert")`:
     Executes CMake configure and Ninja build using the environment configured by `activate.sh`.
   - `gr4_test_oot(project_path: string)`:
     Executes `ctest --output-on-failure` and parses JSON/text test reports.
2. **Automated Error Diagnostics**:
   - `gr4_diagnose_compiler_error(error_log: string)`:
     Specialized rule parser for C++23 template concept failures (e.g., failure to satisfy `gr::BlockLike`, port mismatch, or missing `<complex>` headers), returning pinpoint suggestions to the LLM.

---

### Phase 5: Flowgraph Validation & Control-Plane Simulation

**Goal**: Allow AI to construct, validate, and simulate signal processing flowgraphs via `gnuradio4-control-plane`.

1. **Flowgraph Verification Tools**:
   - `gr4_validate_flowgraph(flowgraph_json: dict)`:
     Verifies graph topology: ensures matching port data types, no dangling inputs, valid sample rate relationships, and acyclic/cyclic scheduling constraints.
   - `gr4_deploy_flowgraph(flowgraph_json: dict, run_duration_seconds?: float)`:
     Submits flowgraph to `gr4cp_server`, starts execution, captures telemetry, and returns throughput/buffer health metrics.
2. **Telemetry & Debugging Tools**:
   - `gr4_inspect_flowgraph_state()`:
     Fetches real-time status of running blocks (samples processed, backpressure, drops).

## 4. IDE Integration & Configuration Guide

### 4.1 Antigravity IDE Integration

In Antigravity IDE, MCP servers are registered in `.gemini/antigravity-ide/mcp/gr4_mcp/mcp_config.json` or through user config:

```json
{
  "mcpServers": {
    "gnuradio4": {
      "command": "python",
      "args": ["-m", "gr4_mcp.server"],
      "env": {
        "GR4_PREFIX": "${workspaceFolder}/install/full"
      }
    }
  }
}
```

## 5. Risk Assessment & Mitigation

| Risk                              | Impact                                                       | Mitigation Strategy                                                                                                                                                                                           |
| :-------------------------------- | :----------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Upstream Git Conflicts**        | Superbuild updates fail to pull/merge cleanly                | **Strict zero-touch policy**: Do not modify tracked files. Register modules strictly via `projects.local.cmake` (git-ignored) or keep MCP code out-of-tree.                                                   |
| **C++23 Concept Strictness**      | LLM hallucinations generate non-compiling blocks             | Provide explicit `gr4://sdk/block-concept` resource and few-shot compiler prompts containing valid C++23 concept templates.                                                                                   |
| **Control Plane Port Collisions** | Port 8080 already in use by host or Docker                   | Emulate [tests/control-plane-smoke.sh](file:///c:/Users/ImMortaLGuruji/Documents/GitHub/gnuradio4/tests/control-plane-smoke.sh#L47): bind to ephemeral dynamic port (`GR4CP_PORT=0`) using `GR4CP_PORT_FILE`. |
| **Platform Variation**            | Compiler discrepancies between GCC 14+, Clang 20+, and macOS | Forward compiler and toolchain paths from the active CMake build directory cache (`CMakeCache.txt`).                                                                                                          |
